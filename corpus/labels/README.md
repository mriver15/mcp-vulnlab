# Label conventions

A **label** is ground truth: one exploitable weakness, described precisely
enough that a human reading it can decide whether a given scanner finding
corresponds to it. The scorecard is only as trustworthy as the labels, so this
directory is deliberately boring and strict.

## Files

| File | Role |
|---|---|
| `label.schema.json` | One label. `$id: urn:mcp-vulnlab:label` |
| `exploits.schema.json` | The `exploits.json` wrapper. `$id: urn:mcp-vulnlab:exploits` |
| `manifest.schema.json` | The `manifest.json` wrapper. `$id: urn:mcp-vulnlab:manifest` |
| `index.json` | Generated by `mcp-vulnlab index`. Committed so coverage is readable without running anything. |

Schemas cross-reference by URN rather than by relative path, so they validate
from any working directory. The harness registers them with `referencing`.

## Where labels live

Labels are **co-located with the challenge** at
`corpus/servers/<slug>/exploits.json`. A challenge has to be self-contained —
you should be able to copy one directory out of this repo and still have the
server, the launch spec, the warning, and the ground truth.

This directory holds the schemas and the generated index, not the labels
themselves.

## Rules

1. **Ids are permanent.** `MCPV-001` stays `MCPV-001` forever. If a challenge is
   deleted, its id is retired rather than recycled — otherwise historical
   scorecards become wrong.
2. **One label, one weakness.** If a tool has two independent problems, that is
   two labels. Bundling them makes recall unmeasurable.
3. **`tool` is the exact MCP tool name.** Scanners are expected to name the tool
   they flag; this is what makes matching possible at all.
4. **`exploit.steps` must reproduce.** If you cannot paste the steps into an MCP
   client and see the weakness, the label is not finished.
5. **`detection.signals` are lowercase substrings.** They exist so the harness can
   map a scanner's free-text finding back to a label. Keep them specific — a
   signal like `"file"` will match half the corpus and inflate recall.
6. **Controls carry no labels.** `kind: "control"` servers have
   `"exploits": []`. Any finding against a control is a false positive.
7. **Severity is per-server, not per-category.** `missing-auth` on a read-only
   health check is not `critical`.

## Validation

```sh
mcp-vulnlab validate
```

Checks, in order:

- every schema file parses and is a valid JSON Schema
- every server directory has `manifest.json`, `exploits.json`, and a `README.md`
- both files validate against their schemas
- `manifest.slug` == `exploits.slug` == directory name
- label `slug` matches, ids are unique corpus-wide, ids match `MCPV-NNN`
- `manifest.categories` agrees with the categories actually present in `exploits.json`
- `kind: control` implies zero exploits, and `kind: vulnerable` implies at least one
- the entrypoint file exists

CI runs this on every push, so a malformed label cannot merge.
